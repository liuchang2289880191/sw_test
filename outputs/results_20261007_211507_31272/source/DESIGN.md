# RMA 路由与端口共享补充实验

日期：2026-10-07。独立目录、独立二进制、独立输出；不修改 `bench/` 或已有结果。

目标是用可复核的干扰特征约束候选片上通信结构，而不是从一次延迟测量宣布真实路由。旧数据记录的平台是 SW39000；继续记录实际 CPU、节点、编译器、cache/LDM 请求和资源共享情况，不直接把结果改称 SW26010Pro。

## 1. 四组实验及其判别问题

| 组 | 改变什么 | 保持什么 | 主要观测 | 能回答什么 |
|---|---|---|---|---|
| E0 完成口径 | 连续单向本地完成；每消息短回信；对称 ping-pong | 核对、数据大小、计时批次 | 发送端 cycles/data、完整 RTT | 旧吞吐是否受发送循环而非往返等待约束 |
| E1 端点共享 | 同一 CPE / 同簇不同 CPE / 分散簇 | 流数、大小、窗口；每条实际流都有单流参考 | 聚合 BW、逐 PE 周期、单流归一化效率 | CPE 发起/接收资源与簇级共享是否留下不同特征 |
| E2 方向共享 | 同向、反向、另一条等长度几何边 | CPE 端点互不重合、流数、大小、窗口 | 归一化聚合吞吐 | 相反方向是否仍表现出共同容量约束 |
| E3 路径干扰 | 一个持续背景流的位置、方向、大小、窗口 | 同一探针、短回信、探针收发 CPE 与簇不被背景端点复用 | 完整 RTT 增量/比值、64-RTT 批均值、实际背景发送数与周期 | 哪种 XY/YX/簇共享假设更符合干扰分布 |

E0 使用 `0→1`、`1→2`、`0→63`，数据 8/64/1024/4096 B。短回信为 8 B，另测与数据等大的对称回复。短回信探针测的是「数据去程＋8 B 回程＋软件响应」的完整 RTT，**不能除以 2 称为单向数据延迟**。所有探针都逐消息检查序号，使用同一测量内核。

E1 每次比较相同数量（2 或 4）的流：

* 发起端：控制为同一簇的不同 CPE，处理为同一个 CPE 发给同样的多个目标。探测 CPE 级发起循环/注入限制，不能把同源软件串行开销全部解释成硬件端口。
* 接收端：控制为同一簇的不同 CPE，处理为同一个 CPE 接收同样的多个源。每条入流有独立 target lane、远端 reply，避免同地址覆盖。
* 簇级对照：相同流数，端点在一簇内或分散到多簇。分散必然改变路径，给两种布局的**每条实际流**单独做前后参考；此项仍不能独立排除路径差异。
* 各端点比较反转流向后复核。两个簇位置（5、10），2/4 流，消息 1/4 KiB，W=1/4/8；非法容量组合自动跳过。

定义 `η=同时运行的聚合BW / Σ(各条实际流的单流BW)`。先在同一作业内比较 η，再比较作业间结果。η 是经验扩展效率，不是硬件端口利用率。每个流的单流参考紧邻对应比较组，前后各一次。

E2 横向 `块5↔块6` 与纵向 `块5↔块9` 均测。例：

```text
同向：块5.A→块6.A，块5.B→块6.B
反向：块5.A→块6.A，块6.B→块5.B
分开：块5.A→块6.A，块9.A→块10.A
```

每个组合都没有共用同一个 CPE。反向若比同向有稳定不同，只能支持方向性资源差异；这些端点仍复用簇，因此不能仅靠这组直接宣布全双工/半双工物理链路。

## 2. 路由探针如何避免“背景早已结束”

E3 内核执行以下协议，无跨 CPE 时钟相减：

1. 64 CPE 在计时外初始化及屏障。
2. 背景发送核发出并完成第一批 W 个请求，向探针发起核写 8 B ready 槽；每个背景源使用独立的 ready 回答字。
3. 探针确认所有背景发送核 ready 后，进行 4 次预热，再计时 N 次数据/回信。背景持续发流量，不使用与探针等长的固定次数循环。
4. 探针结束计时后才向背景源写 8 B stop。背景在批次边界观察 stop 回答字完成后停止，再向各接收端传实际次数；接收端等待相应远端 reply，校验最终槽。
5. 所有测量结束后屏障，再用 DMA 回收数据；没有 DMA 与探针计时重叠。

背景有 2,000,000 次/流的防失控上限；达到上限但未收到 stop 就判该次覆盖失败、停止后续配置，不能作为有效结果。回答字轮询及背景等待 stop 另设周期上限；SDK 调用或最终屏障未返回由主核单项超时兜底。这些检查不能替代调度器作业时间限制。

背景 ready 只证明已启动发流量，不证明始终占满链路。记录实际发送数与源本地周期，确认负载强度；若不同背景位置的负载差异明显，不能只比较探针 RTT 就归因路由。

## 3. 区分候选路径，而不是预先指定真实路径

在 **4×4 几何簇坐标**上定义两种候选算法：XY（先横后纵）和 YX（先纵后横）。它们是实验假设，不能把其边直接称为真实物理 link 或 hop。

探针布局为块 `0→15`、`3→12`、`12→3`、`15→0`。背景流取相邻簇之间的一步通信，剔除探针的两个端点簇。这样背景自身在几何假设中没有 XY/YX 的转弯歧义。

例如探针 `块0→块15`：

```text
候选 XY：0→1→2→3→7→11→15
候选 YX：0→4→8→12→13→14→15

背景 1→2：与 XY 去程同向重合
背景 13→14：与 YX 去程同向重合
背景 5→6：与两种候选去程均不重合
```

这里列的是块 ID，不是 CPE ID。实际 CPE ID 用 `member(block,local)` 生成。

**必须同时考虑回程和方向共享。**即使使用短回信，RTT 仍包含回程。如果实际反向端口共享容量，背景也可能影响候选回信路径。生成器为每组输出：

* XY/YX 去程同向重合边数、反向重合边数；
* XY/YX 回程同向重合边数、反向重合边数；
* 去程/回程共享内部簇数；
* 探针数据大小、回信大小、背景大小与 W。

8 B 数据/8 B 回复是对称对照，可能无法辨别转弯顺序；1024 B 数据/8 B 回复增加去程负载权重，但仍不是纯去程计时。E2 方向结果与 E3 正反探针一起解释。如果两个假设在本实验条件下给出相同干扰特征，报告「无法区分」，不能强选较好看的热图。

## 4. 重复、计时与判读规则

* 默认 5 个独立作业，每项 N=2048；正式建议 4096 或 8192。N 必须为 64 的倍数，不把单个循环当作独立作业重复。
* 每比较组按 ABBA 或 BAAB 执行（A=控制、B=处理），整个组的顺序按固定种子打乱，避免把基线全部跑在前面、负载全部跑在后面。
* 分别输出两次 A、两次 B 和前后单流参考；分析先在每个作业内取 A/B 中位数计算配对效应，再汇总作业间中位数和极差。范围不是置信区间。
* 把「稳定可测」与「较大」分开：效应需超过同组基线漂移，在大多数独立作业上方向一致，且在反向/转置配置复现。不要用单次 0.1% 差异断言物理结构。5 次重复通常不足以稳定估计极小效应。
* 快速组用于排查接口和选择负载；正式组用于假设比较。第二个节点/不同时段复核应当作为独立批次分析，不把不同节点直接混成一个中位数。
* 探针输出完整 RTT；64-RTT 批均值可用于观察时间变化，**不能称为单消息 p95/p99 尾延迟**。批计时及序号检查开销包含在内核中，基线与带背景的探针保持相同代码。
* bulk 带宽仍取活跃核本地周期差最大值，不称为同步全局墙钟带宽。它用于匹配比较；探针 RTT 则完全由发起端自己的计数器测量。

### 路由假设的模型比较

收到数据后，对同一作业内的 `ΔRTT=RTT_loaded−RTT_control` 分析。先看背景负载与基线漂移，再按相同探针大小、背景大小和 W 分层。

候选解释：仅端点/方向；内部簇重合；XY 的去程/回程同向与反向边重合；YX 的对应特征。先检查特征是否可辨识、是否共线；做模型时控制消息与 W，比较留出**整个探针布局**的预测误差，而不是随机留出同一布局的个别重复。系数不唯一或 XY/YX 预测相同，就不输出路径选择结论。

`route_effects.csv` 提供观测与全部候选特征，不自动宣布实际路由。若只有共享簇特征稳定，则支持簇级资源关联；若方向边特征可跨布局预测干扰，才进一步支持相应路径假设。最终确定端口数、逐跳路径或自适应路由仍需硬件事件/官方资料。

## 5. 如何运行

把整个 `rma_supplement/` 上传到服务器的新目录，在**登录节点**执行：

```bash
cd ~/liuchang/sw_test/rma_supplement
# 先检查新的内核和独立槽；仅 6 项，1 个作业。
TOPO_DIAG_ONLY=1 TOPO_TRACE=1 bash run_supplement.sh q_share
# 快速对照，默认 5 个作业、2048 次。
bash run_supplement.sh q_share
# 正式补充组。根据资源情况先查看生成的 plan_info.json，决定机器时间。
TOPO_PROFILE=full TOPO_REPS=4096 TOPO_REPEATS=5 bash run_supplement.sh q_share
```

登录节点需要 Python 3（标准库）、Bash、bsub、swgcc/1473；计算节点只启动原生二进制，不运行 Python、Shell 或子进程。资源请求沿用已跑通的 `-n 1 -cgsp 64 -mpecg 1 -cache_size 0`，但该请求不证明独占。

登录节点只生成计划和编译，不直接执行申威目标二进制，包括 `--validate-plan`。每项参数由计算节点的原生程序在发起 CPE 内核前检查。2026-10-07 已修正旧启动脚本在登录节点调用该选项的问题；回答字初始化也按实际 SDK 的 volatile 类型改成逐项赋值。

### 卡住时的诊断

`diag_05` 是第一项包含持续背景流的探针：`0→63`，数据 64 B、回信 8 B；背景为 `2→4`、`8→16`，1024 B、W=4。前五项完成而它未返回，只能将排查范围缩至新增的协调协议及并发执行；还不能认定哪条通知丢失或哪处硬件资源死锁。

新版在诊断模式默认打印 `TOPO_STAGE`，内核返回时主核打印 `TOPO_RETURN`。阶段包括 `wait_ready`、`probe_ready`、`probe_done`、`stop_sent`、`stop_received`、`metadata_sent`、`wait_metadata`。多个 CPE 的日志可能交错；应结合 PE 与阶段判断，不按显示顺序推断全局时序。

缺少通知时输出 `TOPO_TIMEOUT pe=... stage=... expected=... observed=...`；CSV 同样保存阶段和计数。编号如下：

| stage | 等待/失败的位置 |
|---|---|
| 1 | 批量数据的本地完成 |
| 2 / 3 | ready 的本地完成 / 探针接收 ready |
| 4 / 5 | 探针数据或回信的本地完成 / 远端接收完成 |
| 6 | stop 的本地完成 |
| 7 / 8 | 最终次数元数据的本地完成 / 接收完成 |
| 9 | 按最终次数排空数据回答字 |
| 10 | 背景持续发送时未收到 stop |
| 11 | RMA 接口返回失败 |

stage 是发现问题的位置，未必是最早的原因；例如探针未收到 ready 后会停止背景，未参与测量的应答核也可能报接收超时。

`TOPO_WAIT_TIMEOUT_CYCLES` 默认 1,000,000,000：每个回答字等待设此周期上限；背景从启动起也用该周期上限等待 stop，每 64 批检查一次。没有频率标定，不把它换算秒。主核用 `SIGALRM` 限制每项内核默认 60 秒，配置为 `TOPO_CASE_TIMEOUT_SECONDS=1..3600`；触发时打印 `TOPO_CASE_TIMEOUT` 并以 124 退出，不生成完成标志。SDK 调用若阻塞，可能只有主核超时日志。

轮询读取 volatile 回答字，完成后加入 `memb`；最终次数也以 volatile 读取。这改变了新内核的软件开销，所有新对照使用相同版本，不把旧版与新版绝对延迟直接混合。`TOPO_TRACE=1` 的打印会扰动背景负载，仅用于诊断；正式测量默认 `TOPO_TRACE=0`。有超时、接口错误、数据错误或负载上限命中时停止后续项，失败数据不能进入性能分析。

补丁必须同时更新 `topology_common.h`、`topology_host.c`、`topology_slave.c`、`run_supplement.sh`。结构体布局改变，单独覆盖从核会导致主从核参数不匹配。旧结果和旧实验保持原样。

如果登录节点的 Python 名为 `python`，加 `PYTHON=python`。每次必须使用新输出目录，脚本不能覆盖现有目录。可在本地预览计划，不会提交任务：

```bash
python generate_plan.py --out preview_quick --profile quick --reps 2048
python generate_plan.py --out preview_full --profile full --reps 4096
```

分析可在取回结果后独立重跑：`python analyze.py NEW_RESULTS_DIR`。

### 输出

每个作业有 plan.txt/plan.json、route_features.csv、plan_info.json、资源记录、逐配置 raw CSV、完成标志。分析输出：

* `paired_effects.csv`：逐作业配对效应和基线漂移；
* `summary.csv`：跨作业范围、效应方向一致性与归一化效率；
* `route_effects.csv`：路径探针结果与假设特征；
* `raw_audit.csv`：每个原始 CSV 的 SHA-256。

E3 **处理/控制大于 1 表示 RTT 变长**，与带宽比值“大于 1 更快”的含义相反。E0 的两种协议也不能把其耗时比值称为物理路径惩罚。

## 6. 实现边界与验收

两个数据缓冲各 32 KiB，显著低于旧内核两份 64 KiB；仍需要检查目标编译器的 LDM 布局/运行库余量。host 和计划生成器均检查 `bytes×W≤32 KiB`、`bytes×W×目标入流数≤32 KiB`。没有开启共享 LDM。

每个背景/批量请求有独立目标槽、每条入流有独立 remote reply；下一批在本地完成后复用源槽，背景接收端校验最终每个有效槽。数据模式包含字节位置混合和序号，不以每 256 B 周期重复。探针逐条检查序号/来源，并对最终数据检查全 payload；背景仍不能证明每次中间传输的所有字节都正确。

本地验证使用模拟运行库和线程执行新的 CPE 内核，检查数据、控制握手、计数和失败停止；模拟时间不是申威性能数据。此工作站没有实际 Sunway 编译器/节点，**真实目标编译与运行尚需服务器诊断组验证**。不把本地测试成功写成已测得路由。
